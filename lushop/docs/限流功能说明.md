# HTTP API网关限流功能说明

## 功能概述

在API网关层添加了基于BBR（Bottleneck Bandwidth and Round-trip propagation time）算法的自适应限流机制，能够在系统负载过高时自动限流，保护后端服务不被拖垮。

## 技术实现

### 限流算法：BBR（自适应限流）

BBR是Google提出的一种拥塞控制算法，本项目使用go-kratos的aegis限将其实现：

**核心特点**：
- ✅ **自适应**：根据CPU使用率、QPS、响应时间自动调整
- ✅ **智能限流**：削顶保护，保证超载时系统不被拖垮
- ✅ **高水位运行**：限流后仍能以高水位QPS继续运行

### 限流规则

限流公式：
```
cpu > CPUThreshold AND 
(Now - PrevDrop) < 1s AND 
(MaxPass * MinRt * windows / 1000) < InFlight
```

**指标说明**：
- **CPU**：最近1秒的CPU使用率均值
- **InFlight**：当前正在处理的请求数量
- **MaxPass**：最近时间内单个采样窗口最大的请求数
- **MinRt**：最近时间内单个采样窗口最小的响应时间

## 配置文件

在 `configs/nacosRemote.yaml` 或 Nacos 配置中心添加以下配置：

```yaml
server:
  http:
    addr: 0.0.0.0:8001
    timeout: 1s
    rate_limit:  # 限流配置
      enabled: true  # 是否启用限流
      cpu_threshold: 800  # CPU阈值（0-1000），默认800（80%）
      window_seconds: 10  # 滑动窗口大小（秒），默认10秒
      bucket: 100  # 桶数量，默认100
      whitelist:  # 白名单（不限流的端点）
        - "/lushop.lushop.v1.User/Captcha"
        - "/lushop.lushop.v1.User/Login"
        - "/lushop.lushop.v1.User/Register"
        - "/lushop.lushop.v1.Goods/GetGoodsList"
        - "/lushop.lushop.v1.Goods/GetGoodsDetail"
```

## 配置参数说明

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `enabled` | bool | true | 是否启用限流 |
| `cpu_threshold` | int32 | 800 | CPU阈值，范围0-1000，超过此值触发限流 |
| `window_seconds` | int32 | 10 | 滑动窗口大小（秒） |
| `bucket` | int32 | 100 | 桶数量，用于滑动窗口统计 |
| `whitelist` | []string | [] | 白名单端点，这些端点不受限流影响 |

## 如何配置

### 方式1：修改本地配置文件

编辑 `configs/nacosRemote.yaml`，在 `server.http` 下添加 `rate_limit` 配置。

### 方式2：Nacos配置中心

在Nacos配置中心修改对应的配置项（dataId: lushop.yaml）。

## 限流行为

### 正常情况
- 请求正常通过，不限流
- 记录请求统计信息

### 触发限流时
- 返回HTTP 429状态码
- 错误信息：`"请求过于频繁，请稍后再试"`
- 记录限流日志

### 响应示例

```json
{
  "code": 429,
  "msg": "请求过于频繁，请稍后再试",
  "data": null
}
```

## 白名单机制

### 建议加入白名单的接口

**公开接口**（无需认证）：
```yaml
whitelist:
  # 用户相关
  - "/lushop.lushop.v1.User/Captcha"  # 验证码
  - "/lushop.lushop.v1.User/Login"   # 登录
  - "/lushop.lushop.v1.User/Register" # 注册
  
  # 商品相关
  - "/lushop.lushop.v1.Goods/GetGoodsList"  # 商品列表
  - "/lushop.lushop.v1.Goods/GetGoodsDetail" # 商品详情
  
  # 健康检查
  - "/metrics"  # Prometheus监控端点
```

### 需要限流的接口

**业务接口**（需要认证）：
- 订单接口
- 购物车接口
- 支付接口
- 用户操作接口

这些接口通常操作数据库，需要限流保护。

## 监控和日志

### 日志输出

限流触发时会在日志中输出：
```
level=warn MARKET msg="Rate limit exceeded" endpoint="/lushop.lushop.v1.Order/CreateOrder" error=...
```

### Prometheus指标

限流相关的指标已集成到Prometheus监控中：
- 请求总数
- 限流触发次数
- CPU使用率
- 响应时间

访问 `/metrics` 端点查看详细指标。

## 最佳实践

### 1. CPU阈值设置

- **800（80%）**：一般推荐，平衡性能和稳定性
- **700（70%）**：追求更稳定的系统
- **900（90%）**：追求更高性能

### 2. 窗口大小设置

- **10秒**：默认值，适合大多数场景
- **5秒**：快速响应负载变化，但可能过于敏感
- **30秒**：更平滑的限流，但响应较慢

### 3. 白名单策略

- 将**公开接口**加入白名单
- 将**核心业务接口**保护起来
- **监控接口**通常也需要在白名单中

### 4. 测试建议

1. **压测验证**：使用压测工具验证限流是否生效
2. **监控观察**：观察CPU、QPS、限流触发频率
3. **调整参数**：根据实际情况调整阈值和窗口

## 注意事项

1. ⚠️ **首次使用**：建议从较小的CPU阈值开始，逐步调优
2. ⚠️ **监控告警**：设置CPU和限流触发告警
3. ⚠️ **白名单维护**：定期review白名单，确保合理
4. ⚠️ **性能影响**：BBR算法本身性能开销很小，可放心使用

## 故障排查

### 问题1：限流不生效
**排查**：
- 检查配置是否启用：`enabled: true`
- 检查配置文件是否正确加载
- 查看日志是否有加载配置的信息

### 问题2：误限流
**排查**：
- 调整CPU阈值，适当提高
- 将频繁访问的公开接口加入白名单
- 检查是否是正常流量突然增大

### 问题3：限流过于严格
**排查**：
- 提高CPU阈值（如从800提到900）
- 增大窗口大小（如从10秒提到30秒）
- 扩大白名单范围

## 与现有功能的关系

限流中间件在整个中间件链中的位置：

```
请求 → Recovery → 限流 → 参数验证 → 链路追踪 → JWT → Casbin → 权限 → 日志 → 指标 → 业务逻辑
```

这个位置确保：
- **最高优先级**：限流在参数验证之前，节省验证开销
- **保护系统**：即使其他中间件有问题，限流仍能保护系统

## 总结

限流功能为API网关提供了自动保护能力，能够在高负载情况下：
- ✅ 保护后端服务不被拖垮
- ✅ 保持系统稳定性
- ✅ 自动适应负载变化
- ✅ 灵活的白名单配置

建议在生产环境启用此功能，并根据实际负载情况调整参数。
