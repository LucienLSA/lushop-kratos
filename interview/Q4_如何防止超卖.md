# Q4: 如何防止超卖？

## 🎯 回答框架（2-3分钟）

防止超卖是电商系统的核心问题，我们采用了 **两种方案**：Redis 分布式锁和数据库乐观锁。

## 1. 问题分析

### 1.1 什么是超卖？

```
库存：10 件

并发场景：
用户A：查询库存 10 件 → 扣减 5 件 → 剩余 5 件
用户B：查询库存 10 件 → 扣减 8 件 → 剩余 2 件  ← 超卖了！

实际：扣减了 13 件，但库存只有 10 件
```

### 1.2 为什么会超卖？

```go
// ❌ 错误代码：没有并发控制
func DeductInventory(goodsId int64, nums int32) error {
    // 1. 查询库存
    var inv Inventory
    db.Where("goods_id = ?", goodsId).First(&inv)
    
    // 2. 判断库存（此时可能有其他请求也在执行）
    if inv.Stocks < nums {
        return errors.New("库存不足")
    }
    
    // 3. 扣减库存（并发写入，导致超卖）
    inv.Stocks -= nums
    db.Save(&inv)
    
    return nil
}
```

**问题**：
- 多个请求同时读取库存（都是 10）
- 都判断库存足够
- 都执行扣减操作
- 最终库存变成负数

## 2. 方案对比

| 方案 | 性能 | 可靠性 | 复杂度 | QPS | 适用场景 |
|------|------|--------|--------|-----|----------|
| **Redis 分布式锁** | 高 | 高 | 中 | 10万+ | 高并发（秒杀） |
| **数据库乐观锁** | 中 | 高 | 低 | 5000+ | 中低并发（日常） |
| **数据库悲观锁** | 低 | 高 | 低 | 1000+ | 低并发 |
| **预扣库存** | 极高 | 中 | 高 | 50万+ | 超高并发 |

## 3. 方案1：Redis 分布式锁（推荐）

### 3.1 实现原理

```
请求1                    Redis                   MySQL
  │                       │                       │
  │ ① SETNX lock:1001     │                       │
  │──────────────────────>│                       │
  │                       │ 获取锁成功             │
  │<──────────────────────│                       │
  │                       │                       │
  │ ② 查询库存             │                       │
  │───────────────────────────────────────────────>│
  │<───────────────────────────────────────────────│ 库存：10
  │                       │                       │
  │ ③ 扣减库存             │                       │
  │───────────────────────────────────────────────>│
  │<───────────────────────────────────────────────│ 成功
  │                       │                       │
  │ ④ DEL lock:1001       │                       │
  │──────────────────────>│                       │
  │                       │ 释放锁                 │
  
请求2（等待请求1完成）
  │                       │                       │
  │ ① SETNX lock:1001     │                       │
  │──────────────────────>│                       │
  │                       │ 获取锁失败（等待）     │
```

### 3.2 代码实现

```go
func (r *InventoryRepo) Deduct(ctx context.Context, goodsId, nums int32) error {
    lockKey := fmt.Sprintf("lock:inventory:%d", goodsId)
    lockValue := uuid.New().String()  // 唯一标识，防止误删
    
    // 1. 获取分布式锁（10秒超时）
    lock, err := r.redis.SetNX(ctx, lockKey, lockValue, 10*time.Second).Result()
    if err != nil {
        return fmt.Errorf("redis error: %w", err)
    }
    
    if !lock {
        return errors.New("系统繁忙，请稍后重试")
    }
    
    // 2. 确保锁被释放（使用 Lua 脚本防止误删）
    defer func() {
        script := `
            if redis.call("get", KEYS[1]) == ARGV[1] then
                return redis.call("del", KEYS[1])
            else
                return 0
            end
        `
        r.redis.Eval(ctx, script, []string{lockKey}, lockValue)
    }()
    
    // 3. 查询库存
    var inv Inventory
    if err := r.db.Where("goods_id = ?", goodsId).First(&inv).Error; err != nil {
        return fmt.Errorf("query inventory failed: %w", err)
    }
    
    // 4. 判断库存是否足够
    if inv.Stocks < nums {
        return errors.New("库存不足")
    }
    
    // 5. 扣减库存
    inv.Stocks -= nums
    inv.UpdatedAt = time.Now()
    
    if err := r.db.Save(&inv).Error; err != nil {
        return fmt.Errorf("deduct inventory failed: %w", err)
    }
    
    log.Infof("deduct inventory success: goodsId=%d, nums=%d, remaining=%d", 
        goodsId, nums, inv.Stocks)
    
    return nil
}
```

### 3.3 优化：Lua 脚本原子操作

**更高性能的方案**：直接在 Redis 中扣减库存，减少数据库压力。

```lua
-- deduct_inventory.lua
local key = KEYS[1]
local nums = tonumber(ARGV[1])

-- 获取当前库存
local stocks = redis.call('GET', key)

-- 库存不存在或不足
if not stocks or tonumber(stocks) < nums then
    return 0  -- 库存不足
end

-- 扣减库存
redis.call('DECRBY', key, nums)
return 1  -- 扣减成功
```

```go
func (r *InventoryRepo) DeductWithLua(ctx context.Context, goodsId, nums int32) error {
    script := `
        local key = KEYS[1]
        local nums = tonumber(ARGV[1])
        local stocks = redis.call('GET', key)
        if not stocks or tonumber(stocks) < nums then
            return 0
        end
        redis.call('DECRBY', key, nums)
        return 1
    `
    
    key := fmt.Sprintf("inventory:%d", goodsId)
    result, err := r.redis.Eval(ctx, script, []string{key}, nums).Int()
    
    if err != nil {
        return fmt.Errorf("redis eval failed: %w", err)
    }
    
    if result == 0 {
        return errors.New("库存不足")
    }
    
    // 异步同步到 MySQL（最终一致性）
    go r.syncToMySQL(goodsId, nums)
    
    return nil
}

// 异步同步到 MySQL
func (r *InventoryRepo) syncToMySQL(goodsId int64, nums int32) {
    err := r.db.Model(&Inventory{}).
        Where("goods_id = ?", goodsId).
        Update("stocks", gorm.Expr("stocks - ?", nums)).Error
    
    if err != nil {
        log.Errorf("sync to mysql failed: %v", err)
        // 可以发送消息到队列，稍后重试
    }
}
```

### 3.4 优点与缺点

**优点**：
- ✅ 性能高（Redis 内存操作，QPS 可达 10万+）
- ✅ 支持跨服务（多个实例共享锁）
- ✅ 可以设置超时，避免死锁
- ✅ 适合高并发场景（秒杀）

**缺点**：
- ❌ 需要 Redis（增加系统依赖）
- ❌ 锁粒度较粗（按商品ID加锁）
- ❌ 需要处理 Redis 故障

## 4. 方案2：数据库乐观锁

### 4.1 实现原理

使用 `version` 字段实现乐观锁：

```sql
-- 1. 添加 version 字段
ALTER TABLE inventory ADD COLUMN version INT DEFAULT 0;

-- 2. 更新时检查 version
UPDATE inventory 
SET stocks = stocks - #{nums}, 
    version = version + 1
WHERE goods_id = #{goodsId} 
  AND stocks >= #{nums}
  AND version = #{oldVersion};

-- 3. 如果 affected_rows = 0，说明有并发冲突，需要重试
```

### 4.2 代码实现

```go
func (r *InventoryRepo) DeductWithOptimisticLock(ctx context.Context, goodsId, nums int32) error {
    maxRetries := 3
    
    for i := 0; i < maxRetries; i++ {
        // 1. 查询库存和版本号
        var inv Inventory
        if err := r.db.Where("goods_id = ?", goodsId).First(&inv).Error; err != nil {
            return fmt.Errorf("query inventory failed: %w", err)
        }
        
        // 2. 判断库存
        if inv.Stocks < nums {
            return errors.New("库存不足")
        }
        
        // 3. 使用乐观锁更新
        result := r.db.Model(&Inventory{}).
            Where("goods_id = ? AND version = ? AND stocks >= ?", 
                goodsId, inv.Version, nums).
            Updates(map[string]interface{}{
                "stocks":     gorm.Expr("stocks - ?", nums),
                "version":    gorm.Expr("version + 1"),
                "updated_at": time.Now(),
            })
        
        if result.Error != nil {
            return fmt.Errorf("update inventory failed: %w", result.Error)
        }
        
        // 4. 检查是否更新成功
        if result.RowsAffected > 0 {
            log.Infof("deduct inventory success: goodsId=%d, nums=%d, retry=%d", 
                goodsId, nums, i)
            return nil  // 成功
        }
        
        // 5. 失败则重试
        log.Warnf("optimistic lock conflict, retry %d/%d", i+1, maxRetries)
        time.Sleep(time.Millisecond * 10)
    }
    
    return errors.New("扣减库存失败，请重试")
}
```

### 4.3 优点与缺点

**优点**：
- ✅ 无需额外组件（只需 MySQL）
- ✅ 实现简单
- ✅ 数据库保证原子性

**缺点**：
- ❌ 性能较差（数据库操作）
- ❌ 高并发下重试次数多
- ❌ 可能出现活锁（一直重试失败）

## 5. 方案3：数据库悲观锁

### 5.1 实现原理

使用 `SELECT ... FOR UPDATE` 锁定行：

```sql
-- 1. 开启事务
BEGIN;

-- 2. 锁定行（其他事务无法读写）
SELECT * FROM inventory WHERE goods_id = #{goodsId} FOR UPDATE;

-- 3. 扣减库存
UPDATE inventory SET stocks = stocks - #{nums} WHERE goods_id = #{goodsId};

-- 4. 提交事务
COMMIT;
```

### 5.2 代码实现

```go
func (r *InventoryRepo) DeductWithPessimisticLock(ctx context.Context, goodsId, nums int32) error {
    // 开启事务
    tx := r.db.Begin()
    defer func() {
        if r := recover(); r != nil {
            tx.Rollback()
        }
    }()
    
    // 1. 锁定行
    var inv Inventory
    if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
        Where("goods_id = ?", goodsId).
        First(&inv).Error; err != nil {
        tx.Rollback()
        return fmt.Errorf("query inventory failed: %w", err)
    }
    
    // 2. 判断库存
    if inv.Stocks < nums {
        tx.Rollback()
        return errors.New("库存不足")
    }
    
    // 3. 扣减库存
    inv.Stocks -= nums
    if err := tx.Save(&inv).Error; err != nil {
        tx.Rollback()
        return fmt.Errorf("deduct inventory failed: %w", err)
    }
    
    // 4. 提交事务
    return tx.Commit().Error
}
```

### 5.3 优点与缺点

**优点**：
- ✅ 实现简单
- ✅ 强一致性

**缺点**：
- ❌ 性能差（锁定行，其他请求等待）
- ❌ 容易死锁
- ❌ 不适合高并发

## 6. 方案4：预扣库存（进阶）

适用于秒杀等极高并发场景。

### 6.1 流程图

```
下单                支付成功              订单取消
  │                    │                    │
  ▼                    ▼                    ▼
预扣 Redis          确认扣减 MySQL       归还 Redis + MySQL
```

### 6.2 代码实现

```go
// 1. 下单时预扣库存（Redis）
func (s *OrderService) CreateOrder(ctx context.Context, req *OrderRequest) error {
    key := fmt.Sprintf("inventory:%d", req.GoodsId)
    
    // 预扣 Redis 库存
    stocks, err := s.redis.DecrBy(ctx, key, int64(req.Nums)).Result()
    if err != nil {
        return fmt.Errorf("redis error: %w", err)
    }
    
    if stocks < 0 {
        // 库存不足，回滚
        s.redis.IncrBy(ctx, key, int64(req.Nums))
        return errors.New("库存不足")
    }
    
    // 创建订单（异步）
    go s.createOrderAsync(req)
    
    return nil
}

// 2. 支付成功后确认扣减（MySQL）
func (s *OrderService) ConfirmOrder(ctx context.Context, orderId int64) error {
    order, _ := s.getOrder(orderId)
    
    // 扣减 MySQL 库存
    return s.inventoryRepo.Deduct(ctx, order.GoodsId, order.Nums)
}

// 3. 订单取消时归还库存（Redis + MySQL）
func (s *OrderService) CancelOrder(ctx context.Context, orderId int64) error {
    order, _ := s.getOrder(orderId)
    
    // 归还 Redis 库存
    key := fmt.Sprintf("inventory:%d", order.GoodsId)
    s.redis.IncrBy(ctx, key, int64(order.Nums))
    
    // 归还 MySQL 库存
    return s.inventoryRepo.Return(ctx, order.GoodsId, order.Nums)
}
```

## 7. 实际选择建议

| 场景 | 推荐方案 | QPS | 原因 |
|------|---------|-----|------|
| **秒杀活动** | Redis锁 + Lua脚本 | 10万+ | 高并发，需要极致性能 |
| **日常下单** | 数据库乐观锁 | 5000+ | 并发不高，实现简单 |
| **分布式系统** | Redis 分布式锁 | 10万+ | 跨服务，需要共享锁 |
| **超高并发** | 预扣库存 | 50万+ | 性能最好，但实现复杂 |
| **低并发** | 数据库悲观锁 | 1000+ | 实现简单，强一致性 |

## 💡 面试加分回答

**问**：你们项目用的哪种方案？为什么？

**答**：
"我们项目采用了 **Redis 分布式锁** 方案，主要考虑：

1. **高并发需求**：我们的商品可能有秒杀活动，需要支持高并发
2. **分布式系统**：我们有多个订单服务实例，需要共享锁
3. **性能要求**：Redis 内存操作，QPS 可达 10万+，满足需求

具体实现：
- 使用 `SETNX` 获取锁，设置 10秒超时
- 使用 Lua 脚本释放锁，防止误删
- 锁粒度是商品ID，不同商品可以并发处理

我们也考虑过数据库乐观锁，但：
- 性能较差（数据库操作）
- 高并发下重试次数多
- 不适合秒杀场景

所以最终选择了 Redis 分布式锁。当然，如果 Redis 不可用，我们会降级到数据库乐观锁。"

## 🎯 总结

防止超卖的核心方案：
1. ✅ **Redis 分布式锁**（高并发推荐）
2. ✅ **数据库乐观锁**（中低并发推荐）
3. ✅ **Lua 脚本**（性能优化）
4. ✅ **预扣库存**（超高并发场景）

关键点：
- ⭐ 并发控制（锁或版本号）
- ⭐ 原子操作（Lua 脚本或数据库事务）
- ⭐ 幂等性（防止重复扣减）
- ⭐ 降级方案（Redis 故障时降级到数据库）
