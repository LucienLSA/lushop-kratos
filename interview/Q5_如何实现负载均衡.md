# Q5: 如何实现负载均衡？

## 🎯 回答框架（1-2分钟）

我们使用 **Consul + gRPC 客户端负载均衡**。

## 1. 整体架构

```
┌─────────────────────────────────────────────┐
│         Consul (服务注册中心)                 │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ Goods-1  │  │ Goods-2  │  │ Goods-3  │  │
│  │ :50052   │  │ :50053   │  │ :50054   │  │
│  └──────────┘  └──────────┘  └──────────┘  │
│       ↑              ↑              ↑       │
│       │ 注册         │ 注册         │ 注册  │

                       │ 发现

                ┌──────────────┐
                │ Order Service│
```

## 2. 服务注册

### 2.1 注册流程

```
服务启动
   │
   ▼
创建 Consul 客户端
   │
   ▼
注册服务信息
├── 服务名：lushop.goods.service
├── 地址：127.0.0.1
├── 端口：50052
├── 标签：v1.0, goods
└── 健康检查：gRPC 健康检查
   │
   ▼
Consul 定期健康检查（每10秒）
   │
   ├─> 健康：保留在服务列表
   └─> 不健康：30秒后自动注销
```

### 2.2 代码实现

```go
// internal/server/registry.go
func RegisterService(conf *conf.Registry, logger log.Logger) (registry.Registrar, error) {
    // 1. 创建 Consul 客户端
    config := consulAPI.DefaultConfig()
    config.Address = conf.Consul.Address  // 如：127.0.0.1:8500
    config.Scheme = conf.Consul.Scheme    // 如：http
    
    client, err := consulAPI.NewClient(config)
    if err != nil {
        return nil, fmt.Errorf("create consul client failed: %w", err)
    }
    
    // 2. 生成唯一服务ID
    serviceID := fmt.Sprintf("%s-%s", conf.ServiceName, uuid.New().String())
    
    // 3. 注册服务
    registration := &consulAPI.AgentServiceRegistration{
        ID:      serviceID,                    // 唯一ID
        Name:    conf.ServiceName,             // 服务名
        Address: conf.Host,                    // 服务地址
        Port:    conf.Port,                    // 服务端口
        Tags:    []string{"v1.0", "goods"},    // 标签
        
        // 健康检查配置
        Check: &consulAPI.AgentServiceCheck{
            GRPC:                           fmt.Sprintf("%s:%d", conf.Host, conf.Port),
            Interval:                       "10s",   // 每10秒检查一次
            Timeout:                        "5s",    // 超时时间
            DeregisterCriticalServiceAfter: "30s",  // 30秒后注销不健康服务
        },
    }
    
    if err := client.Agent().ServiceRegister(registration); err != nil {
        return nil, fmt.Errorf("register service failed: %w", err)
    }
    
    logger.Infof("register service success: %s", serviceID)
    
    // 4. 创建 Kratos 注册器
    return consul.New(client, consul.WithHealthCheck(true)), nil
}
```

### 3.1 发现流程

```

创建 gRPC 连接

├── Goods-2: 127.0.0.1:50053
└── Goods-3: 127.0.0.1:50054
   │

gRPC 客户端负载均衡
   │
   ├─> 请求1 → Goods-1
   ├─> 请求2 → Goods-2
   ├─> 请求3 → Goods-3
   └─> 请求4 → Goods-1 (循环)
```

### 3.2 代码实现

```go
// internal/data/goods.go
func NewGoodsClient(conf *conf.Registry, logger log.Logger) (goodsv1.GoodsClient, error) {
    // 1. 创建 Consul 服务发现
    consulConfig := consulAPI.DefaultConfig()
    consulConfig.Address = conf.Consul.Address
    
    consulClient, err := consulAPI.NewClient(consulConfig)
    if err != nil {
        return nil, fmt.Errorf("create consul client failed: %w", err)
    }
    
    dis := consul.New(consulClient)
    
    // 2. 创建 gRPC 连接（自动负载均衡）
    conn, err := grpc.DialInsecure(
        context.Background(),
        grpc.WithEndpoint("discovery:///lushop.goods.service"),  // 服务名
        grpc.WithDiscovery(dis),                                  // 服务发现
        grpc.WithBalancerName("round_robin"),                     // 负载均衡算法
        grpc.WithTimeout(5*time.Second),                          // 超时时间
    )
    
    if err != nil {
        return nil, fmt.Errorf("create grpc connection failed: %w", err)
    }
    
    logger.Info("create goods client success")
    
    // 3. 创建 gRPC 客户端
    return goodsv1.NewGoodsClient(conn), nil
}
```

## 4. 负载均衡算法

### 4.1 算法对比

| 算法 | 说明 | 适用场景 | 配置 |
|------|------|----------|------|
| **round_robin** | 轮询 | 服务性能相同 | `grpc.WithBalancerName("round_robin")` |
| **pick_first** | 选择第一个可用 | 主备模式 | `grpc.WithBalancerName("pick_first")` |
| **random** | 随机选择 | 简单场景 | 自定义实现 |
| **weighted** | 加权轮询 | 服务性能不同 | 自定义实现 |
| **least_request** | 最少请求 | 负载不均 | 自定义实现 |

### 4.2 轮询算法（Round Robin）

**示例**：
```
服务列表：[Goods-1, Goods-2, Goods-3]

请求1 → Goods-1
请求2 → Goods-2
请求3 → Goods-3
请求4 → Goods-1  ← 循环
请求5 → Goods-2
请求6 → Goods-3
...
```

**优点**：
- ✅ 简单易实现
- ✅ 负载分布均匀
- ✅ 无状态

**缺点**：
- ❌ 不考虑服务性能差异
- ❌ 不考虑服务负载情况

### 4.3 加权轮询（Weighted Round Robin）

**场景**：服务器性能不同

```
服务列表：
├── Goods-1: 权重 5 (高性能服务器)
├── Goods-2: 权重 3 (中性能服务器)
└── Goods-3: 权重 2 (低性能服务器)

请求分配：
Goods-1: 50% (5/10)
Goods-2: 30% (3/10)
Goods-3: 20% (2/10)
```

**自定义实现**：

```go
type WeightedBalancer struct {
    services []ServiceInstance
    current  int
    mu       sync.Mutex
}

type ServiceInstance struct {
    Address string
    Weight  int
}

func (b *WeightedBalancer) Pick() string {
    b.mu.Lock()
    defer b.mu.Unlock()
    
    // 计算总权重
    totalWeight := 0
    for _, svc := range b.services {
        totalWeight += svc.Weight
    }
    
    // 根据权重选择
    b.current = (b.current + 1) % totalWeight
    
    sum := 0
    for _, svc := range b.services {
        sum += svc.Weight
        if b.current < sum {
            return svc.Address
        }
    }
    
    return b.services[0].Address
}
```

## 5. 健康检查

### 5.1 健康检查机制

```
Consul Agent
   │
   │ 每10秒检查一次
   ▼
gRPC Health Check
   │
   ├─> 检查数据库连接
   ├─> 检查 Redis 连接
   ├─> 检查依赖服务
   └─> 返回健康状态
   │
   ├─> SERVING (健康)
   ├─> NOT_SERVING (不健康)
   └─> UNKNOWN (未知)
   │
   ▼
Consul 更新服务状态
   │
   ├─> 健康：保留在服务列表
   └─> 不健康：从服务列表移除
```

### 5.2 实现 gRPC 健康检查

```go
// internal/server/health.go
import "google.golang.org/grpc/health/grpc_health_v1"

type HealthServer struct {
    db    *gorm.DB
    redis *redis.Client
}

func (s *HealthServer) Check(ctx context.Context, req *grpc_health_v1.HealthCheckRequest) (*grpc_health_v1.HealthCheckResponse, error) {
    // 1. 检查数据库连接
    if err := s.checkDatabase(); err != nil {
        log.Errorf("database health check failed: %v", err)
        return &grpc_health_v1.HealthCheckResponse{
            Status: grpc_health_v1.HealthCheckResponse_NOT_SERVING,
        }, nil
    }
    
    // 2. 检查 Redis 连接
    if err := s.checkRedis(); err != nil {
        log.Errorf("redis health check failed: %v", err)
        return &grpc_health_v1.HealthCheckResponse{
            Status: grpc_health_v1.HealthCheckResponse_NOT_SERVING,
        }, nil
    }
    
    // 3. 检查依赖服务（可选）
    if err := s.checkDependencies(); err != nil {
        log.Warnf("dependencies health check failed: %v", err)
        // 依赖服务不健康，但本服务仍可用
    }
    
    // 4. 返回健康状态
    return &grpc_health_v1.HealthCheckResponse{
        Status: grpc_health_v1.HealthCheckResponse_SERVING,
    }, nil
}

func (s *HealthServer) checkDatabase() error {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()
    
    return s.db.WithContext(ctx).Raw("SELECT 1").Error
}

func (s *HealthServer) checkRedis() error {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()
    
    return s.redis.Ping(ctx).Err()
}

func (s *HealthServer) checkDependencies() error {
    // 检查依赖的其他服务
    return nil
}

// Watch 方法（流式健康检查）
func (s *HealthServer) Watch(req *grpc_health_v1.HealthCheckRequest, stream grpc_health_v1.Health_WatchServer) error {
    ticker := time.NewTicker(5 * time.Second)
    defer ticker.Stop()
    
    for {
        select {
        case <-ticker.C:
            resp, _ := s.Check(context.Background(), req)
            if err := stream.Send(resp); err != nil {
                return err
            }
        case <-stream.Context().Done():
            return nil
        }
    }
}
```

## 6. 故障转移

### 6.1 自动故障转移

```
初始状态：
Order Service → [Goods-1, Goods-2, Goods-3]

Goods-2 故障：
   │
   ▼
Consul 检测到 Goods-2 不健康
   │
   ▼
从服务列表移除 Goods-2
   │
   ▼
更新后的服务列表：
Order Service → [Goods-1, Goods-3]  ← 自动故障转移

Goods-2 恢复：
   │
   ▼
Consul 检测到 Goods-2 健康
   │
   ▼
重新加入服务列表
   │
   ▼
Order Service → [Goods-1, Goods-2, Goods-3]
```

## 7. 客户端 vs 服务端负载均衡

### 7.1 对比

| 维度 | 客户端负载均衡 | 服务端负载均衡 |
|------|---------------|---------------|
| **实现方式** | 客户端选择服务实例 | 通过负载均衡器转发 |
| **性能** | 高（无中间层） | 中（多一跳） |
| **单点故障** | 无 | 有（负载均衡器） |
| **复杂度** | 高（客户端实现） | 低（集中管理） |
| **适用场景** | 微服务内部调用 | 外部流量接入 |

### 7.2 我们的选择

**微服务内部**：客户端负载均衡（gRPC + Consul）
- ✅ 性能好（无中间层）
- ✅ 无单点故障
- ✅ 动态感知服务变化

**外部流量**：服务端负载均衡（Nginx/Kong）
- ✅ 统一入口
- ✅ 安全控制
- ✅ 协议转换（HTTP → gRPC）

## 💡 面试加分回答

**问**：为什么选择客户端负载均衡？

**答**：
"我们选择客户端负载均衡主要考虑：

1. **性能**：客户端直接调用服务，无中间层，减少网络延迟
2. **无单点故障**：不依赖负载均衡器，避免单点故障
3. **动态感知**：通过 Consul 实时感知服务上下线，自动故障转移
4. **灵活性**：可以根据业务需求选择不同的负载均衡算法

具体实现：
- 使用 Consul 作为服务注册中心
- gRPC 客户端内置负载均衡
- 采用 Round Robin 算法（服务性能相同）
- 配置健康检查，自动剔除故障节点

当然，对于外部流量（如前端请求），我们使用 Nginx 作为服务端负载均衡，提供统一入口和安全控制。"

## 🎯 总结

负载均衡的核心要点：
1. ✅ **服务注册**（Consul）
2. ✅ **服务发现**（gRPC + Consul）
3. ✅ **负载均衡算法**（Round Robin）
4. ✅ **健康检查**（gRPC Health Check）
5. ✅ **故障转移**（自动剔除不健康节点）

优势：
- ⭐ 性能好（客户端负载均衡）
- ⭐ 高可用（自动故障转移）
- ⭐ 动态扩缩容（实时感知服务变化）
- ⭐ 无单点故障
