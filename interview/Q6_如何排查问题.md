# Q6: 如何排查微服务问题？

## 🎯 回答框架（2-3分钟）

我们主要使用 **Jaeger 分布式链路追踪** 来排查问题，配合 Prometheus 监控和日志系统。

## 1. Jaeger 链路追踪

### 1.1 工作原理

```
用户请求
   │
   ▼
API Gateway ──────> Order Service ──────> Goods Service
   │ TraceID            │ TraceID            │ TraceID
   │ (生成)              │ (传递)              │ (传递)
   ▼                    ▼                    ▼
Span-1               Span-2               Span-3
   │                    │                    │
   └────────────────────┴────────────────────┘
                       │
                       ▼
                Jaeger Collector
                       │
                       ▼
                Jaeger Storage (ES/Cassandra)
                       │
                       ▼
                  Jaeger UI
```

### 1.2 核心概念

| 概念 | 说明 | 示例 |
|------|------|------|
| **Trace** | 一次完整的请求链路 | 用户下单的整个流程 |
| **Span** | 一个服务的一次调用 | Order Service 处理订单 |
| **TraceID** | 唯一标识一次请求 | abc123def456 |
| **SpanID** | 唯一标识一个 Span | span001 |
| **Parent SpanID** | 父 Span 的 ID | 用于构建调用关系 |

### 1.3 Trace 示例

```

│
├─ Span-1: API Gateway (50ms)
│  ├─ operation: HTTP /api/order/create
│  ├─ start: 2024-01-01 10:00:00.000
│  └─ end: 2024-01-01 10:00:00.050
│
├─ Span-2: Order Service (2100ms)
│  ├─ operation: CreateOrder
│  ├─ start: 2024-01-01 10:00:00.010
│  ├─ end: 2024-01-01 10:00:02.110
│  │

│  │  ├─ start: 2024-01-01 10:00:00.020
│  │  ├─ end: 2024-01-01 10:00:02.020
```

## 2. 实际排查案例

### 案例1：接口响应慢

**问题**：用户反馈下单接口很慢，需要 3 秒才返回。

#### 步骤1：在 Jaeger UI 中搜索

```
访问：http://localhost:16686

筛选条件：
- Service: lushop.order.service
- Operation: CreateOrder
- Min Duration: 2s
- Limit: 20
```

#### 步骤2：查看调用链路

```
TraceID: abc123def456
│
├─ API Gateway (50ms)
├─ Order Service (100ms)
│  ├─ Goods Service (2000ms)  ← 发现瓶颈！
│  │  └─ MySQL Query (1950ms)  ← 慢查询
│  └─ Inventory Service (50ms)
└─ Total: 3000ms
```

#### 步骤3：定位具体问题

点击 Goods Service 的 Span，查看详细信息：

```json
{
  "operation": "GetGoodsDetail",
  "duration": "2000ms",
  "tags": {
    "db.statement": "SELECT * FROM goods WHERE id = ?",
    "db.type": "mysql",
    "db.instance": "lushop_goods"
  },
  "logs": [
    {
      "timestamp": "2024-01-01 10:00:00.030",
      "message": "start query goods"
    },
    {
      "timestamp": "2024-01-01 10:00:01.980",
      "message": "query goods success"
    }
  ]
}
```

**发现问题**：SQL 查询耗时 1950ms，没有使用索引！

#### 步骤4：解决问题

```sql
-- 添加索引
ALTER TABLE goods ADD INDEX idx_id (id);

-- 优化查询
-- 之前：SELECT * FROM goods WHERE id = ?
-- 之后：SELECT id, name, price FROM goods WHERE id = ?
```

#### 步骤5：验证效果

再次测试，耗时降到 200ms：

```
TraceID: def456ghi789
│
├─ API Gateway (50ms)
├─ Order Service (100ms)
│  ├─ Goods Service (50ms)  ← 优化后
│  │  └─ MySQL Query (30ms)  ← 使用索引
│  └─ Inventory Service (50ms)
└─ Total: 200ms
```

### 案例2：服务调用失败

**问题**：订单创建失败，提示"商品服务不可用"。

#### 步骤1：查看 Jaeger

```
TraceID: xyz789abc123
│
├─ API Gateway (10ms)
├─ Order Service (50ms)
│  └─ Goods Service (Error)  ← 调用失败
│     └─ Error: connection refused
└─ Total: 60ms
```

#### 步骤2：查看 Span 详情

```json
{
  "operation": "GetGoodsDetail",
  "duration": "5ms",
  "tags": {
    "error": true,
    "error.kind": "ConnectionError",
    "peer.address": "127.0.0.1:50052"
  },
  "logs": [
    {
      "timestamp": "2024-01-01 10:00:00.010",
      "level": "error",
      "message": "dial tcp 127.0.0.1:50052: connection refused"
    }
  ]
}
```

**发现问题**：Goods Service 不可用（端口 50052 无法连接）。

#### 步骤3：排查原因

```bash
# 1. 检查服务是否运行
ps aux | grep goods

# 2. 检查端口是否监听
netstat -tlnp | grep 50052

# 3. 查看服务日志
tail -f /var/log/goods.log

# 4. 检查 Consul 注册
curl http://localhost:8500/v1/catalog/service/lushop.goods.service
```

**发现**：Goods Service 进程崩溃了。

#### 步骤4：查看崩溃原因

```bash
# 查看 panic 日志
grep "panic" /var/log/goods.log

# 输出：
# panic: runtime error: invalid memory address or nil pointer dereference
# goroutine 123 [running]:
# service/goods/internal/service.(*GoodsService).GetGoodsDetail(...)
```

**原因**：空指针引用导致 panic。

#### 步骤5：修复并重启

```go
// 修复代码：添加 nil 检查
func (s *GoodsService) GetGoodsDetail(ctx context.Context, req *pb.GoodsRequest) (*pb.GoodsResponse, error) {
    if req == nil {
        return nil, errors.New("request is nil")
    }
    
    // ...
}
```

### 案例3：数据不一致

**问题**：订单创建成功，但库存没有扣减。

#### 步骤1：查看完整调用链

```
TraceID: consistency_issue_001
│
├─ API Gateway (50ms)
├─ Order Service (100ms)
│  ├─ Create Order (50ms)  ← 订单创建成功
│  └─ Send MQ Message (10ms)  ← 发送消息成功
│
└─ Inventory Service (未找到 Span)  ← 消息未消费？
```

#### 步骤2：检查消息队列

```bash
# 查看消息堆积
./mqadmin topicStatus -n localhost:9876 -t order_inventory_topic

# 输出：
# Consumer Group: inventory_consumer_group
# Diff Total: 1000  ← 有 1000 条消息未消费
```

**发现问题**：消息堆积，Inventory Service 没有消费消息。

#### 步骤3：排查消费者

```bash
# 查看消费者状态
./mqadmin consumerProgress -n localhost:9876 -g inventory_consumer_group

# 输出：
# Consumer Group: inventory_consumer_group
# Client IP: 127.0.0.1
# Status: OFFLINE  ← 消费者离线
```

**原因**：Inventory Service 重启后，消费者没有正常启动。

#### 步骤4：修复并验证

```bash
# 重启 Inventory Service
systemctl restart inventory-service

# 查看消息消费情况
./mqadmin topicStatus -n localhost:9876 -t order_inventory_topic

# 输出：
# Diff Total: 0  ← 消息已全部消费
```

## 3. 配合其他工具排查

### 3.1 Prometheus 监控

```bash
# 查看 QPS
rate(http_requests_total[5m])

# 查看错误率
rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m])

# 查看 P99 延迟
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

# 查看 goroutine 数量
go_goroutines
```

### 3.2 日志查询

使用 TraceID 关联日志：

```bash
# 查询指定 TraceID 的所有日志
grep "abc123def456" /var/log/*.log

# 输出：
# /var/log/order.log: [2024-01-01 10:00:00] [TraceID: abc123def456] create order start
# /var/log/goods.log: [2024-01-01 10:00:00] [TraceID: abc123def456] query goods start
# /var/log/inventory.log: [2024-01-01 10:00:02] [TraceID: abc123def456] deduct inventory start
```

### 3.3 数据库慢查询日志

## 5. 常见问题排查技巧

### 5.1 接口超时

**排查步骤**：
1. Jaeger 查看调用链，找到耗时最长的 Span
2. 检查是否有慢查询（数据库、Redis）
3. 检查是否有外部 API 调用慢
4. 检查是否有大量数据传输

**常见原因**：
- 数据库慢查询（没有索引）
- Redis 大 key 操作
- 外部 API 超时
- 网络延迟

### 5.2 服务调用失败

**排查步骤**：
1. Jaeger 查看 Error 标记的 Span
2. 查看错误信息（Tags/Logs）
3. 检查服务是否可用（Consul）
4. 检查网络连接（ping/telnet）

**常见原因**：
- 服务不可用（崩溃、重启）
- 网络问题（防火墙、路由）
- 参数错误（nil、类型不匹配）
- 权限问题（认证失败）

### 5.3 数据不一致

**排查步骤**：
1. Jaeger 追踪完整调用链
2. 检查每个步骤的数据
3. 检查消息队列状态
4. 检查事务提交情况

**常见原因**：
- 消息未消费（消费者离线）
- 事务未提交（代码 bug）
- 补偿失败（重试次数不够）
- 网络分区（数据同步延迟）

## 6. 最佳实践

### 6.1 添加有用的 Tags

```go
span := trace.SpanFromContext(ctx)

// 添加业务标签
span.SetAttributes(
    attribute.String("user.id", userId),
    attribute.String("order.sn", orderSn),
    attribute.Int64("goods.id", goodsId),
)

// 添加数据库标签
span.SetAttributes(
    attribute.String("db.statement", sql),
    attribute.String("db.type", "mysql"),
)

// 添加错误标签
if err != nil {
    span.SetAttributes(
        attribute.Bool("error", true),
        attribute.String("error.message", err.Error()),
    )
}
```

### 6.2 添加有用的 Logs

```go
span.AddEvent("start query goods")
span.AddEvent("query goods success", trace.WithAttributes(
    attribute.Int("result.count", len(goods)),
))
```

### 6.3 使用 TraceID 关联日志

```go
// 从 context 中获取 TraceID
span := trace.SpanFromContext(ctx)
traceID := span.SpanContext().TraceID().String()

// 日志中包含 TraceID
log.Infof("[TraceID: %s] create order start", traceID)
```

## 💡 面试加分回答

**问**：如何快速定位微服务问题？

**答**：
"我们主要使用 Jaeger 分布式链路追踪：

**排查流程**：
1. 在 Jaeger UI 中搜索慢请求或错误请求
2. 查看完整调用链，找到耗时最长或报错的 Span
3. 查看 Span 详情（Tags/Logs），了解具体错误信息
4. 使用 TraceID 关联日志，查看详细日志
5. 配合 Prometheus 监控，查看服务状态
6. 修复问题后，再次测试验证

**实际案例**：
有一次用户反馈下单很慢，我通过 Jaeger 发现是商品服务的数据库查询耗时 2 秒，查看 SQL 发现没有使用索引。添加索引后，耗时降到 30ms，问题解决。

**优势**：
- 可视化调用链，一目了然
- 精确定位瓶颈（到具体的 Span）
- TraceID 关联日志，方便排查
- 支持采样，不影响性能"
