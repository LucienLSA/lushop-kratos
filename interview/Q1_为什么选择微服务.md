# Q1: 为什么选择微服务？

## 🎯 回答框架（1-2分钟）

我们选择微服务架构主要基于以下几个考虑：

## 1. 业务复杂度

电商系统涉及用户、商品、订单、库存等多个业务领域，每个领域都有独立的业务逻辑和数据模型。如果用单体架构，代码会非常庞大（可能超过 10万行），难以维护。

**举例**：
- 用户模块：注册、登录、信息管理、权限控制
- 商品模块：商品管理、分类、搜索、推荐
- 订单模块：购物车、下单、支付、退款
- 库存模块：库存设置、扣减、归还、预警

这些模块如果都放在一个项目里，代码耦合严重，改一个地方可能影响其他模块。

## 2. 团队协作

我们团队有 6-8 个开发人员，微服务可以让不同的人负责不同的服务，减少代码冲突，提高开发效率。

**单体架构的问题**：
- 多人修改同一个代码库，Git 冲突频繁
- 代码审查困难，PR 动辄上千行
- 测试互相影响，A 的改动可能导致 B 的功能出问题

**微服务的优势**：
- 每个人负责独立的服务，代码隔离
- 可以独立开发、测试、部署
- 团队可以并行工作，提高效率

## 3. 技术选型灵活

不同服务可以根据需求选择不同的技术栈：

| 服务 | 技术选型 | 原因 |
|------|---------|------|
| 商品搜索 | ElasticSearch | 需要全文检索和复杂查询 |
| 库存管理 | Redis | 需要高性能和高并发 |
| 订单数据 | MySQL | 需要事务支持和数据一致性 |
| 用户画像 | MongoDB | 需要灵活的文档存储 |

单体架构只能用一套技术栈，无法针对不同场景优化。

## 4. 独立部署和扩展

### 水平扩展
- **单体架构**：只能整体扩展，即使只有订单模块压力大，也要部署整个应用
- **微服务架构**：订单服务压力大时，可以单独扩容 3-5 个实例，不影响其他服务

```
单体架构扩展：
App (100MB) × 5 = 500MB 内存

微服务扩展：
Order (20MB) × 5 = 100MB 内存  ← 节省资源
```

### 故障隔离
- **单体架构**：某个模块出问题（如内存泄漏），整个系统崩溃
- **微服务架构**：商品服务挂了，订单服务仍然可以正常工作（降级处理）

### 独立发布
- **单体架构**：修改一个小功能，需要重启整个应用，影响所有用户
- **微服务架构**：只需要重启修改的服务，其他服务不受影响

## 5. 技术演进

单体架构后期很难重构，微服务可以逐步演进：

```
阶段1：单体应用
└── All in One

阶段2：拆分核心服务
├── 单体应用（非核心功能）
└── 订单服务（核心业务独立）

阶段3：完全微服务化
├── 用户服务
├── 商品服务
├── 订单服务
├── 库存服务
└── ...
```

这种渐进式演进降低了风险，可以边拆分边验证。

## 📊 对比表格

| 维度 | 单体架构 | 微服务架构 |
|------|---------|-----------|
| **开发复杂度** | 低（一个项目） | 高（多个项目） |
| **部署** | 简单（一次部署） | 复杂（多次部署） |
| **扩展性** | 差（只能整体扩展） | 好（按需扩展） |
| **技术栈** | 统一（受限） | 灵活（自由选择） |
| **团队协作** | 困难（代码冲突多） | 容易（独立开发） |
| **故障隔离** | 差（一处故障全挂） | 好（服务隔离） |
| **启动速度** | 慢（加载所有模块） | 快（只加载本服务） |
| **资源占用** | 少（一个进程） | 多（多个进程） |
| **数据一致性** | 容易（本地事务） | 困难（分布式事务） |
| **调试难度** | 低（单进程调试） | 高（跨服务调试） |

## ⚖️ 权衡与取舍

### 微服务不是银弹

微服务增加了系统复杂度，需要完善的基础设施：

| 需求 | 解决方案 | 成本 |
|------|---------|------|
| 服务注册发现 | Consul | 需要学习和维护 |
| 配置中心 | Nacos | 增加运维成本 |
| 链路追踪 | Jaeger | 需要额外资源 |
| 分布式事务 | RocketMQ | 实现复杂 |
| API 网关 | Kong/Nginx | 增加网络层 |
| 服务监控 | Prometheus + Grafana | 需要搭建监控体系 |

### 什么时候不应该用微服务？

- ❌ **团队规模小**（< 5人）：维护成本 > 收益
- ❌ **业务简单**：CRUD 应用，没必要拆分
- ❌ **初创项目**：业务不稳定，频繁重构
- ❌ **没有 DevOps 能力**：无法支撑复杂的部署和运维

### 什么时候应该用微服务？

- ✅ **团队规模大**（> 10人）：需要并行开发
- ✅ **业务复杂**：多个业务领域，边界清晰
- ✅ **高并发场景**：需要独立扩展某些服务
- ✅ **技术多样化**：不同模块需要不同技术栈
- ✅ **有完善的基础设施**：有 DevOps 团队支持

## 💡 面试加分回答

**问**：你们项目适合用微服务吗？

**答**：
"我们项目是一个电商平台，有以下特点：
1. 业务复杂度高，涉及 6 个核心领域
2. 团队有 8 个开发人员，需要并行开发
3. 订单和库存模块需要高并发支持
4. 我们有完善的基础设施（Consul、Nacos、Jaeger）

所以微服务架构是合适的选择。

但我也清楚微服务的代价：
- 增加了系统复杂度
- 需要处理分布式事务
- 需要完善的监控和运维

如果是一个小型项目或初创团队，我会建议先用单体架构，等业务稳定后再考虑拆分。"

## 🎯 总结

选择微服务的核心原因：
1. ✅ **业务复杂**：多个领域，需要独立管理
2. ✅ **团队协作**：多人并行开发，减少冲突
3. ✅ **技术灵活**：不同场景用不同技术
4. ✅ **独立扩展**：按需扩容，节省资源
5. ✅ **故障隔离**：一个服务挂了不影响全局

但要注意：
- ⚠️ 微服务不是银弹
- ⚠️ 要评估团队能力和项目规模
- ⚠️ 要有完善的基础设施支持
