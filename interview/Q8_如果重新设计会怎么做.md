# Q8: 如果重新设计会怎么做？

## 🎯 回答框架（2-3分钟）

如果重新设计这个项目，我会在以下几个方面做改进。

## 1. 引入 Service Mesh（Istio）

### 1.1 现状问题

服务治理逻辑（负载均衡、熔断、限流）耦合在业务代码中：

```go
// 现在：业务代码中处理服务治理
conn, err := grpc.DialInsecure(
    ctx,
    grpc.WithEndpoint("discovery:///lushop.goods.service"),
    grpc.WithDiscovery(dis),
    grpc.WithBalancerName("round_robin"),  // 负载均衡
    grpc.WithTimeout(5*time.Second),       // 超时
)
```

### 1.2 改进方案

使用 Istio 将治理逻辑下沉到基础设施层：

```yaml
# Istio VirtualService 配置
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: goods-service
spec:
  hosts:
  - goods-service
  http:
  - route:
    - destination:
        host: goods-service
        subset: v1
      weight: 90
    - destination:
        host: goods-service
        subset: v2
      weight: 10  # 灰度发布
    timeout: 5s
    retries:
      attempts: 3
      perTryTimeout: 2s
```

### 1.3 优势

- ✅ 业务代码更简洁（无需关心服务治理）
- ✅ 统一的治理策略（配置化管理）
- ✅ 支持灰度发布（流量控制）
- ✅ 多语言支持（不限于 Go）

## 2. 使用 CQRS 模式

### 2.1 现状问题

读写使用同一个数据库，高并发下性能瓶颈：

```go
// 现在：读写都用 MySQL
func GetOrderList(userId int64) ([]*Order, error) {
    var orders []*Order
    db.Where("user_id = ?", userId).Find(&orders)
    return orders, nil
}
```

### 2.2 改进方案

读写分离 + 事件溯源：

```go
// 写模型（Command）
type OrderCommandService struct {
    db       *gorm.DB
    eventBus EventBus
}

func (s *OrderCommandService) CreateOrder(cmd CreateOrderCommand) error {
    // 1. 创建订单
    order := &Order{...}
    s.db.Create(order)
    
    // 2. 发布事件
    event := OrderCreatedEvent{
        OrderId: order.ID,
        UserId:  order.UserId,
        Amount:  order.Amount,
    }
    s.eventBus.Publish(event)
    
    return nil
}

// 读模型（Query）
type OrderQueryService struct {
    redis *redis.Client
    es    *elasticsearch.Client
}

func (s *OrderQueryService) GetOrderList(query OrderQuery) ([]*Order, error) {
    // 从 Redis 或 ES 查询（性能更好）
    return s.redis.Get(query)
}

// 事件处理器（同步读模型）
func HandleOrderCreatedEvent(event OrderCreatedEvent) {
    // 更新 Redis
    redis.Set("order:"+event.OrderId, event)
    
    // 更新 ES（支持复杂查询）
    es.Index("orders", event)
}
```

### 2.3 优势

- ✅ 读写性能都能优化
- ✅ 支持复杂查询（ES）
- ✅ 历史数据可追溯
- ✅ 读写分离，互不影响

## 4. 引入 API 限流降级

### 4.1 现状问题

缺少限流和降级机制，高并发下可能雪崩。

### 4.2 改进方案

使用 Sentinel 实现限流降级：

```go
import "github.com/alibaba/sentinel-golang/core/flow"

// 限流规则
func initFlowRules() {
    _, err := flow.LoadRules([]*flow.Rule{
        {
            Resource:               "CreateOrder",
            TokenCalculateStrategy: flow.Direct,
            ControlBehavior:        flow.Reject,
            Threshold:              100,  // QPS 100
            StatIntervalInMs:       1000,
        },
    })
}

// 使用限流
func (s *OrderService) CreateOrder(ctx context.Context, req *OrderRequest) error {
    entry, err := sentinel.Entry("CreateOrder")
    if err != nil {
        return errors.New("系统繁忙，请稍后重试")
    }
    defer entry.Exit()
    
    // 业务逻辑
    return s.createOrder(ctx, req)
}
```

**降级规则**：

```go
// 熔断降级
func initCircuitBreakerRules() {
    _, err := circuitbreaker.LoadRules([]*circuitbreaker.Rule{
        {
            Resource:         "GoodsService",
            Strategy:         circuitbreaker.SlowRequestRatio,
            RetryTimeoutMs:   3000,
            MinRequestAmount: 10,
            StatIntervalMs:   5000,
            MaxAllowedRtMs:   50,
            Threshold:        0.5,  // 50% 慢请求触发熔断
        },
    })
}
```

### 4.3 优势

- ✅ 防止系统过载
- ✅ 快速失败，避免雪崩
- ✅ 保护核心服务

## 5. 使用 Kubernetes 部署

### 5.1 现状问题

手动部署，运维成本高。

### 5.2 改进方案

使用 Kubernetes 实现自动化部署：

```yaml
# Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
      - name: order-service
        image: lushop/order-service:v1.0
        ports:
        - containerPort: 50053
        resources:
          requests:
            memory: "256Mi"
            cpu: "250m"
          limits:
            memory: "512Mi"
            cpu: "500m"
        livenessProbe:
          grpc:
            port: 50053
          initialDelaySeconds: 10
          periodSeconds: 10
        readinessProbe:
          grpc:
            port: 50053
          initialDelaySeconds: 5
          periodSeconds: 5

---
# Service
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  selector:
    app: order-service
  ports:
  - port: 50053
    targetPort: 50053
  type: ClusterIP

---
# HPA (自动扩缩容)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

### 5.3 优势

- ✅ 自动化部署
- ✅ 自动扩缩容
- ✅ 滚动更新
- ✅ 自愈能力

## 7. 引入 CI/CD

### 7.1 改进方案

使用 GitLab CI/CD 实现自动化流程：

```yaml
# .gitlab-ci.yml
stages:
  - test
  - build
  - deploy

# 单元测试
test:
  stage: test
  script:
    - go test -v -race -coverprofile=coverage.out ./...
    - go tool cover -html=coverage.out -o coverage.html
  coverage: '/coverage: \d+.\d+% of statements/'

# 构建镜像
build:
  stage: build
  script:
    - docker build -t lushop/order-service:$CI_COMMIT_SHA .
    - docker push lushop/order-service:$CI_COMMIT_SHA

# 部署到 K8s
deploy:
  stage: deploy
  script:
    - kubectl set image deployment/order-service order-service=lushop/order-service:$CI_COMMIT_SHA
    - kubectl rollout status deployment/order-service
  only:
    - main
```

### 7.2 优势

- ✅ 自动化测试
- ✅ 自动化部署
- ✅ 快速交付
