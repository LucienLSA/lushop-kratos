# Q2: 如何拆分服务？

## 🎯 回答框架（1-2分钟）

我们采用 **DDD（领域驱动设计）** 的方法拆分服务。

## 1. 识别业务领域

首先分析业务，识别出核心领域：

```
电商系统业务分析
│
├── 用户领域 (User Domain)
│   ├── 用户注册
│   ├── 用户登录
│   ├── 用户信息管理
│   └── 密码管理
│
├── 认证领域 (Auth Domain)  ← 独立出来，其他服务也需要
│   ├── JWT Token 管理
│   ├── 图形验证码
│   ├── 短信验证码
│   └── 黑名单管理
│
├── 商品领域 (Goods Domain)
│   ├── 商品 CRUD
│   ├── 商品分类
│   ├── 商品搜索
│   └── 商品推荐
│
├── 订单领域 (Order Domain)
│   ├── 购物车管理
│   ├── 订单创建
│   ├── 订单支付
│   └── 订单查询
│
├── 库存领域 (Inventory Domain)  ← 独立出来，需要高性能
│   ├── 库存设置
│   ├── 库存扣减
│   ├── 库存归还
│   └── 库存预警
│
└── 用户操作领域 (UserOp Domain)
    ├── 地址管理
    ├── 商品收藏
    └── 用户留言
```

## 2. 拆分原则

### 2.1 单一职责原则（SRP）

每个服务只负责一个业务领域，不要混杂多个职责。

**❌ 错误示例**：
```
用户服务
├── 用户管理
├── 订单管理  ← 不应该在这里
└── 商品收藏  ← 不应该在这里
```

**✅ 正确示例**：
```
用户服务 - 只负责用户相关
├── 用户注册
├── 用户登录
└── 用户信息管理

订单服务 - 只负责订单相关
├── 订单创建
└── 订单查询

用户操作服务 - 负责用户的操作行为
├── 地址管理
└── 商品收藏
```

### 2.2 高内聚低耦合

**高内聚**：相关的功能放在一起
- 订单创建和订单查询放在订单服务
- 购物车和订单放在一起（都是下单流程）

**低耦合**：减少服务间的依赖
- 订单服务不直接访问商品数据库
- 通过 gRPC 调用商品服务获取数据

### 2.3 数据独立

每个服务有自己的数据库，避免共享数据库。

```
❌ 错误：共享数据库
┌─────────────┐     ┌─────────────┐
│ Order Svc   │────>│             │
└─────────────┘     │   MySQL     │<──── 数据耦合！
┌─────────────┐     │             │
│ Goods Svc   │────>│             │
└─────────────┘     └─────────────┘

✅ 正确：独立数据库
┌─────────────┐     ┌─────────────┐
│ Order Svc   │────>│  Order DB   │
└─────────────┘     └─────────────┘
       │ gRPC
       ↓
┌─────────────┐     ┌─────────────┐
│ Goods Svc   │────>│  Goods DB   │
└─────────────┘     └─────────────┘
```

### 2.4 业务闭环

尽量让一个服务能独立完成一个业务流程，减少跨服务调用。

**示例**：订单服务
```go
// ✅ 好的设计：订单服务内部完成大部分逻辑
func (s *OrderService) CreateOrder(ctx context.Context, req *OrderRequest) error {
    // 1. 验证用户（调用用户服务）
    user := s.userClient.GetUser(ctx, req.UserId)
    
    // 2. 验证商品（调用商品服务）
    goods := s.goodsClient.GetGoods(ctx, req.GoodsId)
    
    // 3. 计算价格（本地计算）
    amount := s.calculateAmount(goods, req.Nums)
    
    // 4. 创建订单（本地数据库）
    order := s.createOrder(user, goods, amount)
    
    // 5. 扣减库存（发送消息，异步处理）
    s.sendInventoryMessage(order)
    
    return nil
}
```

### 3.3 详细功能划分

#### User Service (用户服务)
```go
// 用户相关的核心功能
type UserService interface {
    // 用户注册
    Register(ctx context.Context, req *RegisterRequest) (*User, error)
    
    // 用户登录
    Login(ctx context.Context, req *LoginRequest) (*Token, error)
    
    // 获取用户信息
    GetUser(ctx context.Context, userId int64) (*User, error)
    
    // 更新用户信息
    UpdateUser(ctx context.Context, user *User) error
}
```

#### UserAuth Service (认证服务)
```go
// 认证相关功能（独立出来，其他服务也需要）
type UserAuthService interface {
    // 生成 Token
    GenerateToken(ctx context.Context, userId int64) (string, error)
    
    // 验证 Token
    ValidateToken(ctx context.Context, token string) (*Claims, error)
    
    // 生成验证码
    GenerateCaptcha(ctx context.Context) (*Captcha, error)
    
    // 验证验证码
    VerifyCaptcha(ctx context.Context, captchaId, code string) (bool, error)
}
```

#### Goods Service (商品服务)
```go
// 商品相关功能
type GoodsService interface {
    // 商品列表
    GetGoodsList(ctx context.Context, req *GoodsListRequest) ([]*Goods, error)
    
    // 商品详情
    GetGoodsDetail(ctx context.Context, goodsId int64) (*Goods, error)
    
    // 创建商品
    CreateGoods(ctx context.Context, goods *Goods) error
    
    // 更新商品
    UpdateGoods(ctx context.Context, goods *Goods) error
}
```

#### Order Service (订单服务)
```go
// 订单相关功能
type OrderService interface {
    // 创建订单（核心功能）
    CreateOrder(ctx context.Context, req *OrderRequest) (*Order, error)
```

#### Inventory Service (库存服务)
```go
// 库存相关功能（独立出来，需要高性能）
type InventoryService interface {
```

## 4. 拆分时的考虑因素

### 4.1 不要过度拆分

**❌ 过度拆分的问题**：
```
用户服务
├── 用户注册服务
├── 用户登录服务
├── 用户信息服务
└── 用户密码服务  ← 太细了！
```

**✅ 合理拆分**：
```
用户服务
├── 注册、登录、信息管理都在一起
└── 这些功能高度相关，放在一起更合理
```

**经验**：
- 一般 5-10 个服务比较合适
- 要匹配团队规模（每个服务 1-2 人负责）
- 太多服务会增加管理成本

### 4.2 考虑调用频率

**高频调用的功能放在一起**，减少网络开销。

```
❌ 不好的设计
订单服务 ──gRPC──> 购物车服务  ← 每次下单都要调用

✅ 好的设计
订单服务（包含购物车功能）  ← 本地调用，性能更好
```

### 4.3 考虑数据一致性

**需要强一致性的功能放在一个服务**。

```
✅ 订单服务内部
├── 订单创建
└── 订单详情  ← 同一个数据库，强一致性

❌ 跨服务
订单服务 ──消息──> 库存服务  ← 最终一致性
```

### 4.4 考虑性能要求

**高性能要求的功能独立出来**，方便优化和扩展。

```
库存服务（独立）
├── 使用 Redis 缓存
├── 使用分布式锁
└── 可以独立扩容 10 个实例  ← 高并发场景
```

## 5. 拆分后的挑战及解决

| 挑战 | 问题 | 解决方案 |
|------|------|----------|
| **分布式事务** | 订单创建 + 库存扣减 | RocketMQ 事务消息 |
| **服务间调用** | 网络延迟、序列化 | gRPC 高性能通信 |
| **数据一致性** | 最终一致性 | 补偿机制 + 定时检查 |
| **服务治理** | 服务注册、发现 | Consul 服务发现 |
| **配置管理** | 配置分散 | Nacos 配置中心 |
| **链路追踪** | 调用链复杂 | Jaeger 分布式追踪 |
| **服务监控** | 多个服务难监控 | Prometheus + Grafana |

## 💡 面试加分回答

**问**：你们是如何决定拆分粒度的？

**答**：
"我们主要考虑了几个因素：

1. **业务边界**：按照 DDD 的思想，识别出 6 个核心领域
2. **团队规模**：我们有 8 个人，平均每人负责 1 个服务
3. **调用频率**：订单和购物车高频调用，放在一起
4. **性能要求**：库存需要高并发，独立出来方便优化
5. **数据一致性**：需要强一致性的功能放在一个服务

我们也避免了过度拆分，比如没有把用户注册、登录拆成独立服务，因为它们高度相关，拆分后反而增加复杂度。

最终拆分成 6 个服务 + 1 个网关，这个粒度比较合适，既保证了服务的独立性，又不会太复杂。"

## 🎯 总结

服务拆分的核心原则：
1. ✅ **按业务领域拆分**（DDD）
2. ✅ **单一职责**（一个服务一个领域）
3. ✅ **高内聚低耦合**（相关功能放一起）
4. ✅ **数据独立**（每个服务独立数据库）
5. ✅ **不要过度拆分**（5-10 个服务合适）

拆分时要考虑：
- ⚠️ 调用频率（高频调用放一起）
- ⚠️ 数据一致性（强一致放一起）
- ⚠️ 性能要求（高性能独立出来）
- ⚠️ 团队规模（匹配人员配置）
