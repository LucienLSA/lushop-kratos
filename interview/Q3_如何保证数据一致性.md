# Q3: 如何保证数据一致性？

## 🎯 回答框架（2-3分钟）

在分布式系统中，我们采用 **最终一致性** 方案，主要使用 **RocketMQ 事务消息**。

## 1. 典型场景：订单创建 + 库存扣减

这是一个跨服务的分布式事务，需要保证：
- ✅ 订单创建成功 → 库存必须扣减
- ✅ 订单创建失败 → 库存不能扣减
- ✅ 不能出现订单创建了但库存没扣减
- ✅ 不能出现库存扣减了但订单没创建

**为什么是分布式事务？**
- 订单服务和库存服务是两个独立的服务
- 各自有独立的数据库
- 无法使用本地事务（ACID）

## 2. 解决方案：RocketMQ 事务消息

### 2.1 流程图

```
┌─────────────┐         ┌─────────────┐         ┌─────────────┐
│ Order Svc   │         │  RocketMQ   │         │Inventory Svc│
└──────┬──────┘         └──────┬──────┘         └──────┬──────┘
       │                       │                       │
       │ ① 发送半消息           │                       │
       │──────────────────────>│                       │
       │                       │                       │
       │ ② 返回成功             │                       │
       │<──────────────────────│                       │
       │                       │                       │
       │ ③ 执行本地事务         │                       │
       │   (创建订单到DB)       │                       │
       │                       │                       │
       │ ④ 提交/回滚消息        │                       │
       │──────────────────────>│                       │
       │                       │                       │
       │                       │ ⑤ 推送消息             │
       │                       │──────────────────────>│
       │                       │                       │
       │                       │                       │ ⑥ 扣减库存
       │                       │                       │
       │                       │ ⑦ ACK                 │
       │                       │<──────────────────────│
       │                       │                       │
       
       如果网络异常，RocketMQ 会回查本地事务状态
       │                       │                       │
       │ ⑧ 事务回查             │                       │
       │<──────────────────────│                       │
       │                       │                       │
       │ ⑨ 返回事务状态         │                       │
       │──────────────────────>│                       │
```

### 2.2 代码实现

#### 步骤1：发送事务消息

```go
// OrderService - 创建订单
func (s *OrderService) CreateOrder(ctx context.Context, req *OrderRequest) (*Order, error) {
    // 准备消息
    msg := &primitive.Message{
        Topic: "order_inventory_topic",
        Body:  json.Marshal(req),
    }
    
    // 发送事务消息
    result, err := s.producer.SendMessageInTransaction(ctx, msg, 
        // 本地事务执行器
        func(msg *primitive.Message) primitive.LocalTransactionState {
            // 创建订单到数据库
            order := &Order{
                OrderSn: generateOrderSn(),
                UserId:  req.UserId,
                GoodsId: req.GoodsId,
                Nums:    req.Nums,
                Amount:  req.Amount,
                Status:  "UNPAID",
            }
            
            // 执行本地事务
            if err := s.repo.CreateOrder(ctx, order); err != nil {
                log.Errorf("create order failed: %v", err)
                return primitive.RollbackMessageState  // 回滚消息
            }
            
            log.Infof("create order success: %s", order.OrderSn)
            return primitive.CommitMessageState  // 提交消息
        },
    )
    
    if err != nil {
        return nil, err
    }
    
    log.Infof("send transaction message success: %s", result.MsgID)
    return order, nil
}
```

#### 步骤2：事务回查

```go
// OrderService - 事务回查（防止网络异常）
func (s *OrderService) CheckLocalTransaction(msg *primitive.MessageExt) primitive.LocalTransactionState {
    var req OrderRequest
    if err := json.Unmarshal(msg.Body, &req); err != nil {
        log.Errorf("unmarshal message failed: %v", err)
        return primitive.RollbackMessageState
    }
    
    // 查询订单是否存在
    order, err := s.repo.GetOrderByUserId(ctx, req.UserId, req.GoodsId)
    if err != nil {
        log.Errorf("query order failed: %v", err)
        return primitive.RollbackMessageState
    }
    
    if order != nil && order.ID > 0 {
        log.Infof("order exists, commit message: %s", order.OrderSn)
        return primitive.CommitMessageState  // 订单存在，提交消息
    }
    
    log.Warn("order not exists, rollback message")
    return primitive.RollbackMessageState  // 订单不存在，回滚消息
}
```

#### 步骤3：消费消息

```go
// InventoryService - 消费消息（扣减库存）
func (s *InventoryService) ConsumeOrderMessage(ctx context.Context, msgs ...*primitive.MessageExt) (consumer.ConsumeResult, error) {
    for _, msg := range msgs {
        var req OrderRequest
        if err := json.Unmarshal(msg.Body, &req); err != nil {
            log.Errorf("unmarshal message failed: %v", err)
            continue
        }
        
        // 扣减库存
        err := s.repo.DeductInventory(ctx, req.GoodsId, req.Nums)
        if err != nil {
            log.Errorf("deduct inventory failed: %v", err)
            // 返回稍后重试
            return consumer.ConsumeRetryLater, err
        }
        
        log.Infof("deduct inventory success: goodsId=%d, nums=%d", req.GoodsId, req.Nums)
    }
    
    return consumer.ConsumeSuccess, nil
}
```

### 2.3 关键点说明

#### 半消息（Half Message）
- 消息发送到 RocketMQ，但对消费者不可见
- 等待本地事务执行结果
- 如果提交，消费者才能看到消息

#### 事务回查
- 如果网络异常，RocketMQ 不知道本地事务是否成功
- RocketMQ 会定期回查本地事务状态
- 根据查询结果决定提交还是回滚消息

#### 消息重试
- 如果消费失败，RocketMQ 会自动重试
- 最多重试 16 次
- 超过次数会进入死信队列

## 3. 为什么不用 2PC/3PC？

### 3.1 方案对比

| 方案 | 一致性 | 性能 | 可用性 | 复杂度 | 适用场景 |
|------|-------|------|--------|--------|----------|
| **2PC** | 强一致 | 差（阻塞） | 差（单点） | 中 | 金融转账 |
| **3PC** | 强一致 | 差 | 中 | 高 | 很少使用 |
| **TCC** | 最终一致 | 好 | 好 | 高（需补偿） | 支付系统 |
| **事务消息** | 最终一致 | 好 | 好 | 中 | 电商系统 ✅ |
| **Saga** | 最终一致 | 好 | 好 | 高 | 长事务 |

### 3.2 2PC 的问题

```
协调者                参与者1              参与者2
   │                    │                    │
   │ ① 准备阶段          │                    │
   │───────────────────>│                    │
   │───────────────────────────────────────>│
   │                    │                    │
   │ ② 等待响应          │                    │
   │<───────────────────│ YES                │
   │<───────────────────────────────────────│ YES
   │                    │                    │
   │ ③ 提交阶段          │                    │
   │───────────────────>│ COMMIT             │
   │───────────────────────────────────────>│ COMMIT
   │                    │                    │
   
问题：
1. 阻塞：参与者在准备阶段会锁定资源，等待协调者指令
2. 单点故障：协调者挂了，参与者一直阻塞
3. 数据不一致：网络分区时，部分参与者提交，部分回滚
```

### 3.3 选择事务消息的原因

**优点**：
- ✅ **性能好**：异步处理，不阻塞
- ✅ **高可用**：支持事务回查，防止消息丢失
- ✅ **实现相对简单**：不需要补偿逻辑
- ✅ **适合电商场景**：允许短暂不一致（几秒内）

**缺点**：
- ❌ **最终一致性**：不是强一致性
- ❌ **需要消息中间件**：增加系统复杂度

## 4. 其他一致性保证

### 4.1 幂等性

消息可能重复消费，需要保证幂等。

#### 方案1：唯一键约束

```go
// 数据库层面保证
type Order struct {
    ID      int64  `gorm:"primaryKey"`
    OrderSn string `gorm:"uniqueIndex"`  // 唯一索引
    // ...
}

func (r *OrderRepo) CreateOrder(ctx context.Context, order *Order) error {
    // 重复插入会报错：Duplicate entry
    return r.db.Create(order).Error
}
```

#### 方案2：先查询再插入

```go
func (r *OrderRepo) CreateOrderIdempotent(ctx context.Context, order *Order) error {
    // 先查询是否存在
    var existing Order
    r.db.Where("order_sn = ?", order.OrderSn).First(&existing)
    
    if existing.ID > 0 {
        log.Infof("order already exists: %s", order.OrderSn)
        return nil  // 已存在，直接返回成功
    }
    
    // 不存在则创建
    return r.db.Create(order).Error
}
```

#### 方案3：分布式锁

```go
func (r *OrderRepo) CreateOrderWithLock(ctx context.Context, order *Order) error {
    lockKey := "lock:order:" + order.OrderSn
    
    // 获取分布式锁
    lock, err := r.redis.SetNX(ctx, lockKey, "1", 10*time.Second).Result()
    if err != nil || !lock {
        return errors.New("duplicate request")
    }
    defer r.redis.Del(ctx, lockKey)
    
    // 创建订单
    return r.db.Create(order).Error
}
```

### 4.2 补偿机制

如果库存扣减失败，需要取消订单。

```go
func (s *InventoryService) ConsumeOrderMessage(ctx context.Context, msgs ...*primitive.MessageExt) (consumer.ConsumeResult, error) {
    for _, msg := range msgs {
        var req OrderRequest
        json.Unmarshal(msg.Body, &req)
        
        // 尝试扣减库存
        err := s.repo.DeductInventory(ctx, req.GoodsId, req.Nums)
        if err != nil {
            log.Errorf("deduct inventory failed: %v", err)
            
            // 发送补偿消息：取消订单
            s.sendCancelOrderMessage(req.OrderSn)
            
            return consumer.ConsumeSuccess, nil  // 标记消费成功，不再重试
        }
        
        log.Infof("deduct inventory success")
    }
    
    return consumer.ConsumeSuccess, nil
}

// 发送取消订单消息
func (s *InventoryService) sendCancelOrderMessage(orderSn string) {
    msg := &primitive.Message{
        Topic: "order_cancel_topic",
        Body:  []byte(orderSn),
    }
    
    s.producer.SendSync(context.Background(), msg)
}
```

### 4.3 最终一致性检查

定时任务检查数据一致性。

```go
func (s *ConsistencyCheckService) CheckOrderInventory() {
    // 每小时检查一次
    ticker := time.NewTicker(1 * time.Hour)
    defer ticker.Stop()
    
    for range ticker.C {
        // 查询订单但库存未扣减的记录
        inconsistentOrders := s.findInconsistentOrders()
        
        if len(inconsistentOrders) > 0 {
            log.Warnf("found %d inconsistent orders", len(inconsistentOrders))
            
            for _, order := range inconsistentOrders {
                // 重新发送消息
                s.resendInventoryMessage(order)
                
                // 或者人工介入
                s.notifyAdmin(order)
            }
        }
    }
}

func (s *ConsistencyCheckService) findInconsistentOrders() []*Order {
    var orders []*Order
    
    // 查询 30 分钟前创建的订单
    s.db.Where("status = ? AND created_at < ?", 
        "UNPAID", 
        time.Now().Add(-30*time.Minute),
    ).Find(&orders)
    
    // 检查库存是否扣减
    var inconsistent []*Order
    for _, order := range orders {
        // 查询库存扣减记录
        var log InventoryLog
        s.db.Where("order_sn = ?", order.OrderSn).First(&log)
        
        if log.ID == 0 {
            // 库存未扣减
            inconsistent = append(inconsistent, order)
        }
    }
    
    return inconsistent
}
```

## 5. CAP 理论

### 5.1 CAP 定义

- **C (Consistency)**：一致性，所有节点看到的数据相同
- **A (Availability)**：可用性，系统一直可以响应请求
- **P (Partition tolerance)**：分区容错性，网络分区时系统仍能工作

**CAP 定理**：三者只能同时满足两个。

### 5.2 我们的选择：AP

```
┌─────────────────────────────────────┐
│         CAP 三角形                   │
│                                     │
│            C (一致性)                │
│           /  \                      │
│          /    \                     │
│         /      \                    │
│        /        \                   │
│       /          \                  │
│      /            \                 │
│     /              \                │
│    /                \               │
│   /                  \              │
│  A (可用性)──────────── P (分区容错)  │
│                                     │
│  我们选择：AP (最终一致性)           │
└─────────────────────────────────────┘
```

**为什么选择 AP？**

1. **P 是必须的**：分布式系统一定会有网络分区
2. **A 很重要**：电商系统要求高可用，不能因为网络问题就不可用
3. **C 可以放宽**：允许短暂不一致（几秒内），最终一致即可

**示例**：
- 订单创建后，库存可能延迟几秒才扣减
- 用户看到的库存可能不是实时的
- 但最终（几秒内）会达到一致

## 💡 面试加分回答

**问**：为什么不用强一致性方案（如 2PC）？

**答**：
"我们评估了几种方案：

**2PC/3PC**：
- 优点：强一致性
- 缺点：性能差（阻塞）、可用性差（单点故障）
- 不适合电商高并发场景

**TCC**：
- 优点：性能好、强一致性
- 缺点：实现复杂，需要写 Try、Confirm、Cancel 三个接口
- 开发成本高

**事务消息**：
- 优点：性能好、高可用、实现相对简单
- 缺点：最终一致性（但电商场景可以接受）
- 最适合我们的场景

我们的业务允许短暂不一致（几秒内），用户下单后，库存延迟几秒扣减是可以接受的。所以我们选择了事务消息方案，在性能、可用性和实现复杂度之间取得了平衡。"

## 🎯 总结

数据一致性保证的核心方案：
1. ✅ **RocketMQ 事务消息**（主要方案）
2. ✅ **幂等性**（防止重复消费）
3. ✅ **补偿机制**（失败后补偿）
4. ✅ **最终一致性检查**（定时检查）

选择事务消息的原因：
- ⭐ 性能好（异步处理）
- ⭐ 高可用（支持事务回查）
- ⭐ 实现相对简单
- ⭐ 适合电商场景（AP 模型）
